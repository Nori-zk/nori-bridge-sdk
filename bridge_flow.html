Nori Bridge — ETH → nETH Flow

End-to-end deposit & minting flow across Ethereum, the Nori bridge service, and Mina

Phase 1 — Client Preparation Client
1
SCRAM Sign
Client signs a fixed message (e.g. "NoriZK25") with their Mina private key.
Produces a deterministic signatureSCRAM — reproducible from the same key + message on any machine.
2
Create Code Challenge
codeChallenge = Poseidon.hash(signatureSCRAM.toFields())
This Field value is committed on Ethereum (deposit key) and verified on Mina (SCRAM proof) — binding the deposit to the Mina key holder.
▼
Phase 2 — Ethereum Deposit Client → ETH
3
lockTokens(codeChallenge, { value })
Calls the ETH Token Bridge contract. Min deposit: 0.0001 ETH (100 bridge units).
The codeChallenge is stored as the deposit key in lockedTokens and depositKeyToEthAddress maps.
Transaction receipt provides depositBlockNumber — used to track processing status.
▼
Phase 3 — Bridge Processing Autonomous
4
Wait for ETH Finality
Bridge monitors the Ethereum beacon chain until the deposit block reaches finality. Client tracks via WebSocket state.eth topic.
5
SP1 Helios Proof Generation
Bridge generates an SP1 proof covering:
• Ethereum consensus (beacon chain light client sync via Helios)
• MPT storage proof of deposits on the ETH bridge contract
Public values include: inputStoreHash, outputStoreHash, executionStateRoot, verifiedContractDepositsRoot, contractAddress, nextSyncCommitteeHash
6
Proof Conversion (SP1 PLONK → o1js)
SP1 PLONK proof is converted into an o1js-verifiable format (NodeProofLeft).
Output's subtreeVkDigest is verified against on-chain po2. Public inputs digest verified against on-chain pi0.
7
Submit update() to Mina
Bridge service calls NoriTokenBridge.update(ethInput, convertedProof, oldestAction):
• Verifies converted proof against on-chain pi0 and po2
• Validates store hash chain continuity (inputStoreHash must match on-chain state)
• Validates ETH bridge contract address matches on-chain ethTokenBridgeAddress
• Advances latestHead and updates verifiedStateRoot, store hash fields
• Extracts verifiedContractDepositsRoot and dispatches it as a reducer action
• dispatchAndEvict() manages a rolling window of max 32 deposit roots
Client monitors progress via WebSocket topics: state.eth (ETH finality), state.bridge (bridge job stage + block range), timings.notices.transition (stage timing). The getDepositProcessingStatus$ RxJS observable classifies the deposit as: WaitingForEthFinality → WaitingForPreviousJobCompletion → WaitingForCurrentJobCompletion → ReadyToMint (or MissedMintingOpportunity).
▼
Phase 4 — Client Minting Client → Mina
8
computeDepositAttestationWitness()
Once readyToComputeMintProof() resolves, client fetches deposit data from PCS:
GET {pcsUrl}/converted-consensus-mpt-proofs/{depositBlockNumber}
Retrieves all contract_storage_slots — the full set of deposits at that block.
• Finds own deposit by matching codeChallenge
• Builds a Poseidon Merkle tree (depth 16) from all deposit slot leaves
• Returns MerkleTreeContractDepositAttestorInputJson: Merkle path + deposit index + deposit values
9
setUpStorage() — one-time per user
Creates a NoriStorageInterface child account under NoriTokenBridge's token ID.
Sets userKeyHash = Poseidon.hash(userPublicKey.toFields()) and mintedSoFar = 0.
Verification key must match on-chain storageVKHash. Skipped if user already has storage.
10
noriMint(depositAttestationInput, scramWitness)
After canMint() resolves (bridge submitted proof to Mina, deposit root in action window):
On-chain verification (ZK circuit):
① Recompute contractDepositSlotRoot from Merkle witness (path + index + leaf)
② Reducer check: reducer.getActions({fromActionState: windowStart}) → reducer.reduce() to verify root exists in the rolling action window
③ Extract totalLocked and codeChallenge from the deposit attestation
④ Verify SCRAM: verifyCodeChallenge(codeChallenge, signature, sender, message) — proves knowledge of the commitment pre-image + key ownership
⑤ Verify storage: userKeyHash == Poseidon.hash(sender), account is not new
⑥ Calculate amountToMint = totalLocked - mintedSoFar (via NoriStorageInterface.increaseMintedAmount)
⑦ Update mintedSoFar in storage
11
FungibleToken.mint()
NoriTokenBridge calls FungibleToken.mint(userAddress, amountToMint).
Gated by mintLock flag — noriMint() sets it to false, then canMint() callback resets to true. Only noriMint() can trigger minting; direct calls are blocked.
External Services

Real-time bridge state monitoring.
Topics: state.eth, state.bridge, timings.notices.transition
Used by: Phase 3 monitoring, deposit status classification
Proof Conversion Service (PCS)
HTTP API serving converted proofs and ETH contract storage slots.
GET /converted-consensus-mpt-proofs/{blockNumber}
Used by: Step 8 — provides all deposit slots for Merkle tree construction
Ethereum RPC
ETH node for lockTokens transactions and block monitoring
Mina RPC + Archive
Mina node for submitting proofs, fetching accounts, and reading actions
NoriTokenBridge On-Chain State
Identity & Config
adminPublicKey, tokenBaseAddress, storageVKHash, ethTokenBridgeAddress, mintLock
Ethereum Head Tracking
latestHead (beacon slot), verifiedStateRoot, latestHeliusStoreInputHash (high + low), latestVerifiedContractDepositsRoot
Integrity Parameters
noriHeliosProgramPi0 — SP1 program identifier (pi0)
proofConversionPO2 — proof conversion VK digest (po2)
Set by admin post-deploy; changeable without recompile
Action Window (Reducer)
windowStart — action-state hash at window start
windowSize — current count (max 32)
Stores deposit roots as dispatched actions; noriMint() verifies root membership via reducer.reduce()

Security Model

MechanismProtection
SCRAMOnly the Mina key holder who deposited can mint — signature commitment scheme verified inside ZK circuit
Store hash chainSequential proof validation — each proof's inputStoreHash must match on-chain output, preventing gaps/replays
Action windowDeposit roots expire after 32 new submissions — bounded state growth, time-limited minting
mintLockPrevents direct FungibleToken.mint() bypass — only noriMint() can toggle it
storageVKHashEnsures only the correct NoriStorageInterface program runs in the token account
ensureAdminSignatureAdmin-gated setters (pi0, po2, updateStoreHash, adminSetDepositRoot, VK upgrade)
